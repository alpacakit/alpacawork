# Tasks and requests: the common procedure

This file is for coordinators and owners, who create tasks and send requests. Members follow [references/member.md](member.md). A coordinator relaying the user's words writes the request text as ["Relaying the user's words" in Coordinator](coordinator.md#relaying-the-users-words) says, in place of the items below on what to put in it; the last item, on what not to write, still applies.

- If you split work, aim for pieces that an agent can carry through and verify on its own. Keep decisions that change together in one piece as far as possible. Small work need not be split. When you learn of a new connection, revisit the split within the scope you were given. An owner chooses who does each piece (itself, a member or a child) as ["Choosing who does the work" in Owner](owner.md#choosing-who-does-the-work) says.
- `task request -h` gives the launch directory of a new conversation when `--cwd` is left out. To have the work location's instruction files (AGENTS.md and the like) apply from launch, pass `--cwd <absolute path>` with the first request or with a `--new-conversation` request. A continued conversation launches in the same directory as the previous Run.
- When you create a task, put what you can write at that point into field values, and pass them to `task new --values-file` as the absolute path of a UTF-8 file or as `-` (stdin). Values are optional. For the fields and how to write them, follow `alpacawork field get`. For how the coordinator creates tasks, see ["Turning a request into a task" in Coordinator](coordinator.md#turning-a-request-into-a-task).
- Before creating a task, look at the tree with `task list`. An owner creates children under its own task. If a task's purpose turns out to belong to a different parent, move it under that parent (who may move it is in Access in `task move -h`; moving a task under a task removes the user-requested mark).
- Send rework on the same result as a mid-work instruction to the same recipient. Normally continue the same conversation for a send-back or a mid-work instruction to the same recipient, and choose a new conversation when moving on to the next substantial result. Continuing costs a re-read of the old context; starting anew costs building the snapshot and fetching again. Weigh these, including the cache and how the work differs. Do not decide by elapsed time or the number of exchanges alone. Whether the request goes from parent to child, from owner to member, or from coordinator to task, choose by this standard before sending.
- You can change the model or effort and continue the same conversation with the same agent. See `task request -h` for how request, placement and server choices determine the launch values.
- Before choosing how to send the next request, read `task get` for the task and check `context.usedPercent` on the recipient's placement in `agents`.
- Between those two there is a third way: continue the same conversation compacted first (`task request --compact`, or for an owner's own next conversation `task report --next-conversation compact`). Decide in this order; the figures are guides, not the decision on their own.
  1. A new conversation when moving on to the next substantial result, when the direction changed or the whole was rejected (below), when the same finding failed twice, or when a conversation already compacted once fills up again. The snapshot and the request text carry what still holds.
  2. A compacted conversation for the same result's next step (a send-back, the next step of the same flow) when its history should stay (what was tried and failed, small decisions) and `context.usedPercent` is 50 or more. Compacting between instructions leaves room for the next step. Apply this threshold when the percentage is available. Where the agent supports `--compact-focus`, name what the summary should keep (for example "the agreed API shape and the tests that failed").
  3. Otherwise continue as it is. Every agent compacts by itself near its limit, so do not compact for fear of overflowing.
  Each compaction calls the model once (it reads the conversation and writes a summary), so do not make it a ritual.
- When the direction changes, or the recipient clings to an old assumption, reconsider the choice of conversation even for the same result (for how to judge, see ["Reports" in Owner](owner.md#reports)). An evaluation that rejects the result as a whole (such as "hard to understand", "hard to read", "not good enough" or "redo it": anything that rejects the outcome as a whole) is a change of direction, and a new conversation is the default for it. In the same conversation the recipient is pulled along by the assumptions of the rejected approach, so a comparison of costs alone does not overturn this default. Continue the same conversation for a fix that points at a specific place or for an addition to the current result, even when the wording is "hard to read". Even when the words arrive as the answer to a question, a request that rejects the whole and asks for a redo is new work, so send it as an ordinary instruction instead of saving it as an answer, and apply this standard to it (for sorting what to save as an answer from what to send as an ordinary instruction, see ["Relaying the user's words" in Coordinator](coordinator.md#relaying-the-users-words); the handling of other answers does not change).
- Write the previous result into the request text as a read command. For a new conversation, also quote the original words of the rejection (if they arrived as an answer, the full text and the read command for the original question), and pass the approach to drop and the decisions to keep (including the option chosen there and the approvals) as the difference from the old snapshot (see the "Before asking for the next piece of work" item below). For a Run that is unfinished or busy, or whose receipt is unknown, and for words you save as the answer to a question, follow the rules below.
- An owner, too, can save the latest values at a breakpoint in the same save as its report, with `task report --values-file`, and can state with `--next-conversation new` its intent to make the next conversation a new one, or with `--next-conversation compact` (and `--compact-focus`) to continue it compacted first (["Reports" in Owner](owner.md#reports)). Once that Run has ended successfully, the next ordinary instruction and the next automatic launch both follow that choice of conversation. Input that arrives during the work is delivered to the current conversation, and input that arrives after the save cancels the old intent for the next conversation. A new conversation also inherits the record of questions, answers and requests from the same task, but an old awaited reply is closed by the resume rules in ["Questions" in Delivery and completion](lifecycle.md#questions).
- A request to a recipient that is working joins the same work at the next breakpoint of the current work, if the recipient can take it through its input channel (that Run is `joined`; the work and the result are in the `into` Run). If the recipient cannot take it, the request arrives as a continuation after the current run ends.
- Before asking for the next piece of work (parent to child, owner to member, coordinator to task), apply [the question in "Reports" in Owner](owner.md#reports) to the original request, the changes in effect and the done conditions, and to the recipient's result, the counter-evidence and the work you are about to ask for. Read a member's current state from its instructions and the Runs it returned; do not substitute the snapshot of the task it belongs to. For a first request, check how the request contributes to the goal; if the goal is already achieved, do not wake the recipient only to switch conversations. When you change direction, do not write the recipient's values for it; pass the difference from the old snapshot (the old option to drop, and the decisions, approvals and conditions to keep) and the necessary facts in the request text.
- Before sending to a placement that already has Runs, check the runtime and `headRunId` (the latest Run of the placement's conversation; "head" below) of the target placement (`agents`) in `task get`. If a new conversation has already taken on the same work, do not stack another new conversation on it for the old conversation's reasons; decide again from the current result and new grounds. Do not use the latest Run of the whole task, the runtime's `sourceRunIds`, or `reviewRun` in place of head. If requests are waiting in a queue, combine yours into one message or wait for them to finish, and split the work to another recipient if necessary.
- If starting a new conversation, or compacting the existing one, is still needed, pass the `headRunId` you read as `--expected-head-run`, in addition to the task hash and the placement revision, and add `--new-conversation` (or `--compact`) to the same message that carries the instruction you need to send. For a first request, where there is no head, use only the task hash and placement revision conditions; do not treat a read error as a first request. On a conflict, read again starting from whether the new conversation is needed; do not just swap the head or the hash. Do not send a separate message that only switches conversations.
- An explicit request for a new or a compacted conversation sent to an unfinished Run is refused; it does not become a reservation for after the Run ends. Deliver a correction of direction during the work as an ordinary instruction; then either the recipient itself updates the snapshot and its intent for the next conversation at a safe breakpoint, or the requesting side decides again after the Run ends. `--answers` cannot be combined with a new or a compacted conversation, so include the necessary direction and the reasons in the answer to the original question. If the server has already accepted the request, wait for its result; when receipt is unknown or the recipient is busy, first follow the existing procedures for checking and recovery.
- Do not wake a recipient only for a message that is not urgent. Each request you send adds one run for the recipient. Ask for reviews together at breakpoints. As a guide, request work from at most 10 children in one wait cycle ([Waking](lifecycle.md#waking)); if there are more, split them into stages.
- Put what is to be done in the task title and in the first line of the request (not the name of the addressee), so that the work can be read from the screen and from reports.
- Send requests and answers with `task request`, and pass the request text to `--instruction-file` as an absolute path or `-` (there are no options for a title or a description). A task's fields are where the owner reports, so do not put the request text there (a report overwrites them). For a record that does not change the state, use `task comment`, following ["Recording work" in the main skill](../SKILL.md#recording-work).
- Placing an agent does not launch it. It launches only when you send a request (when the owner of a task that is in progress, awaiting review or failed is replaced, except a task awaiting review with no Run, the server delivers a handover to the new owner). `request_accepted` means only that the server took the request in; it does not mean that the agent launched, read it or agreed to it.
- When you place an agent (`agent assign`), decide its agent, model and effort for this work: what the user's words name for this work; else what the project policy says about which agent, model or effort to use, applied to the nature of this work; else name none, and the configured AI order for tasks (`aiStack` in `config get`) decides. Give what you decided as `--ai-stack '[{"agent":"<agent>","values":{"model":"<model>","effort":"<effort>"}}]'`, with every value the words or the policy fix: a value you leave out comes from the configured row for that agent, not from the policy. Given on the placement, it stays the placement's AI in every conversation, ahead of the configured order; `--selected` there covers only the first launch. To use another AI for one request, give `--selected` or `--ai-stack` on `task request`.
- On `agent assign`, `agent handover`, or a request with `--selected` or `--ai-stack`, choose `--placed-as` using the meanings in that command’s help (`default` when you give neither `--ai-stack` nor `--selected`). Include one line with `--placed-note` for an exception.
- In the request text, write concisely the purpose, the done conditions, the necessary information, the work location, what may be changed, what must not be touched, the scope of approval, and the conditions for stopping to consult. Write the conditions for stopping to consult concretely enough that the recipient can tell where to stop within the work you ask for or allow. Do not add documents or formats only for the sake of requesting or splitting work.
- When you ask an agent for a review, include in that request the startup and the cleanup that the review needs.
- Decide how deeply to verify by the weight of the change, and ask for only as much record and evidence as the next decision needs.
- Define the done conditions by the result that resolves the problem and the assurance that is required, and keep them the same across planning, the request, review and acceptance. Within what the user specified and the scope of approval, it is the owner who decides to switch to a different means of verification that can check the required assurance on the real thing; the owner reports the reason.
- In the done conditions, cover failures caused by this change and problems that make the result unusable; do not add conditions only because of separate, pre-existing problems. Return as unverified any failure whose effect on the required assurance, or whose relation to this change, cannot be verified.
- The easier something is to mistake or overlook, and the larger the impact of a failure, the more detail you must give about what to verify, in which situations, and how far. This is the same for a first request and for an additional request.
- Do not write how to do the work, except where the method is itself what is being requested or is needed to stay safe and within the scope of approval. If rounds of trying and fixing are expected, also write the limit on failures and the breakpoints for review. Set the limit to match the weight and the impact of the request.
- Define the purpose and the done conditions from the user's original words and the decisions still in effect. In the request text, pass on the recipient's share, the necessary requirements, constraints and principles, and the unverified points without changing their meaning, and mark any condition that is not in the user's words so that it is recognizable as "a condition the AI added". Do not confuse a summary or an interpretation with the original words.
- When you want the recipient to read an alpacawork record, write the read command (for example `alpacawork task get --task T42`), not a file path. Write the read command for a list of siblings or children only in a request that needs the list.
- Do not write: the common guardrails in this skill (the recipient reads them too); what alpacawork adds to the launch prompt (see ["When you start or resume" in the main skill](../SKILL.md#when-you-start-or-resume)); secrets (the request text stays in the record and can be read from other conversations).
