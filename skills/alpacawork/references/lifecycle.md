# Delivery and completion

## Waking

A wait cycle lasts until every request the owner sent has closed. The user's turn is any state that does not move until the user decides: awaiting review, a question addressed to the user, a failed top task, a failed child that its parent cannot fix, a task stopped at the limit, a delivery whose receipt is unknown, or a task that cannot be woken for some reason (configuration, depth and so on). It appears in the user's list and notifications. The user's proxy is a person, or the coordinator quoting the user's words.

- W0 (request): when a `task request` arrives, its recipient wakes. The sender is the parent, the coordinator, a person, the server (for a handover), or a sibling responsible using a [loan](request.md#letting-two-child-tasks-work-directly).
- W1 (a result arrives): even while other requests are still open, the owner is woken once with all the results that have arrived by then. A request to a member closes when its Run ends (succeeded, failed or stopped). A request to a child closes when the child becomes done, stopped or failed, or is moved (it does not close on a question or a hold). Putting a child on hold or taking it off hold notifies each responsible waiting on an open request to it, including a borrower. Moving an existing task under a task notifies its new parent. Delivering a result does not close another open request.
- W2 (wake at once): a question addressed to an ancestor task wakes that task's current owner even in the middle of a wait cycle. When the requester is the parent, an urgent note or an urgent end report also wakes the parent at once.
- W3 (answer): when an answer to an open question arrives, the current owner of the asking task wakes. An answer with a loan and an answer to a withdrawn or already answered question arrive as instructions (W0).
- If the recipient is running and its input channel is open, the item is passed in as mid-work input. If the channel is not open, the recipient wakes once after the current turn. What arrived becomes handled when the turn that received it ends successfully (there is nothing to mark by hand). Reading it with `task returns` alone does not make it handled.
- What wakes no one: a record, a question to the user, and a task going into awaiting review. A notice alone also does not wake the owner of a failed, held or finished task (what arrives while a task is failed goes into the launch prompt of the retry request). The coordinator and the user are not woken automatically; they learn from the list and notifications.
- The number of automatic launches has a limit. Once it is reached, even urgent items stop, and the user's turn shows "stopped at the limit". The user decides whether to continue. The count returns to 0 when an ordinary `task request` from a person or the coordinator arrives at that task or an ancestor. An answer to an open question (`--answers`) and a record do not reset it (an answer from a person or the coordinator to a closed question is an ordinary instruction, so it does). The coordinator asks for the continuation, quoting the user's words with `--quote`.

## Questions

- A task has at most one awaited reply (an open question it asked, or awaiting review), whoever the recipient is. When a task asks a new question, the server withdraws that task's open question. One question may contain several sub-questions, so when the points multiply, regroup them into one question and ask that (for the steps, see [the owner procedure](owner.md#waking-and-waiting)).
- When the owner goes back to new work, the earlier awaited reply closes. An ordinary instruction to the owner and an automatic continuation (a return from a child or a member, a question addressed to the task, an answer, and so on) each, at the moment the server takes it in, withdraw the task's own old question and return a task that is awaiting review to in progress. The owner's own `doing` report is also a declaration that work has resumed, so it is treated the same way, and it also withdraws a question asked in the same Run.
- An owner that has resumed reads the full text of the withdrawn original question (the question an answer is for), this input and the children's latest status, then gathers the points still needed and asks them again as a new question. The question's record and full text remain, so do not treat a withdrawal as "the decision is settled". When awaiting review was lifted, likewise re-evaluate the result and the latest status before reporting the end again. To save values only, use `task update --values-file`.
- The owner asks a question with `task report --state waiting --ask-to <ancestor Task ID>|user` (for how to write it and how to choose the recipient, see ["Limits of your responsibility and whom to ask" in Owner](owner.md#limits-of-your-responsibility-and-whom-to-ask)). The server fixes the full text as of the moment of asking in the question's record; the source of truth, and the task and question IDs to answer to, stay with the asking task. Only the current owner of the recipient task answers a question addressed to an AI; the user's proxy answers a question addressed to a person. Being able to read does not mean having the right to instruct other branches.
- Read the full text of an original question with `task get --task <asking task> --question <question ID>`. Answer with `task request --task <asking task> --answers <question ID> --instruction-file ...`. An answer takes no version (a question is identified by its ID and its fixed full text). An answer to a withdrawn or already answered question is not discarded: it arrives at that task as an ordinary instruction from whoever was able to answer that question, and the result's `outcome` carries `answers`. The owner judges the reply to the original question together with the current points. An answer to a question that expired through a stop or a move is refused.
- Saving an answer records the answer to the fixed original question as a whole, and only the first one for a given question goes through. That the server took a request in, that it was delivered, that an answer was saved, that the answer actually settles the question, and that it was actually applied are separate facts. The AI that has read the words and the latest snapshot judges what an answer or a new instruction means, which points are unresolved and what work comes next. A question closes on an answer, a withdrawal, the resumption of work, the same task's next question or end report, or expiry through a stop or a move. An owner withdraws a question of its own that is no longer needed, when it is not asking a new one, with `task report --withdraw <question ID>`. Do not reopen a closed question; ask anew only when a further decision is needed.
- A question expires when a move leaves its recipient no longer an ancestor; choose again, from the current tree, whom to ask. Do not revive a question from a notice already received or from an old conversation. Handle holds, failures, limits and the like with the existing resume procedures.

## Done and awaiting review

- When finished, the owner reports with `task report --state done --title "<result>" --description-file <file or ->`. The title and a nonblank description are required; summarize the result, verification and remaining work in the description, even when values or attachments contain the details. A task with the user-requested mark (`userRequested` in `task get`) goes into awaiting review, and no one wakes. Any other task (a child, or a top task created by an agent) becomes done directly, and the request to that task closes. The parent reads the child's result and, if something is missing, asks the same owner for rework with an ordinary `task request` (the child returns to in progress).
- A task cannot finish while it has an unresolved question addressed to it, an open request, a return not yet delivered, an unfinished child (a failed child included) or a running Run (alpacawork refuses). Have a failed child retried and brought to done, or stop it, and then finish. An open question the task asked is withdrawn by the end report.
- Only the user accepts a result that is awaiting review (the coordinator writes it in, quoting the user's words). A fix or a change of definition is passed down by the parent that already holds the right to instruct, or by the user's proxy, with an ordinary `task request --instruction-file ...`.
  - To accept a Run's result, use `task report --state done --about-run <the Run being accepted>`. Take that Run from `reviewRun` in the `task get` of the awaiting-review task that was shown to the user; do not fill it in with whichever Run is latest when you run the command.
  - To accept a result that the user's proxy submitted without a Run (the awaiting-review report has no `runId` and it is the user's turn; `reviewRun` is null), use `task report --state done --expected-task-hash <hash>` with the hash of the task that was shown, and do not fill in a Run or a placement revision.
  - The user's proxy can put a done task that the user requested back into awaiting review with `task report --state waiting --expected-task-hash <hash>`. This needs no agent and no Run, and it creates no question.
- A task that is awaiting review also returns to in progress under the same resume rules as in "Questions" above. A record, and a rewrite of only the task's own values, do not count as resuming.
- Have the same agent continue fixes within what has been approved. In a request that uses a past result, write the Run/submission ID. If what is needed is a decision that changes the purpose, the assurance required, the scope that may be changed, or the scope of what the user specified or approved, or a continuation beyond the failure limit, stop and ask whoever holds that decision.

## Hold

- A hold (`held`) is a mark that pauses automatic continuation for the time being.
  - Putting a task on hold: the user's proxy puts a task in any state on hold with `task report --state held`.
  - Who can take a task off hold: a person, the coordinator quoting the user's words, or the owner of the direct parent can do so explicitly. The coordinator records in `--quote` either the user's current message or the scope of delegation in the project policy; the direct parent takes the task off hold when it judges that the work should continue. The owner of the target task itself cannot take its own task off hold, and its `doing` reports and questions leave the hold in place. If the parent itself is on hold, that parent's direct parent, the coordinator or a person first takes the parent off hold.
  - How to take a task off hold: read `baseState` and the hash from the latest `task get`, and return the task with `task report --task <target> --state <current baseState> --expected-task-hash <hash>`.
  - What arrives during a hold: notices alone, such as results and answers, do not wake the owner automatically; the notices are kept. A direct request can arrive and wake the agent, but the hold stays. After the hold is removed, delivery, work, acceptance and retries of failures follow the normal rules. What an owner can do while on hold is in ["Responsibilities" in Owner](owner.md#responsibilities).

## Failures

- When the owner's Run ends as `failed`, the system makes the task `error`. When the owner's turn ends without leaving an end report, a question or an open request, the task becomes `error` whether the turn ended without a report or a person stopped it (except a Run stopped by a replacement, and a Run stopped before it began). `--state error` cannot be reported by hand.
- While a task is `error`, nothing wakes automatically. The requester decides whether to retry or to stop. If the requester is the parent, the parent asks the same owner to retry with `task request`, or stops the task. If the requester is the user, the task appears in the user's turn and the user decides. When the owner's next Run starts, the task returns to `doing`.
- A Run that is `needs_review` has not ended yet. A member's Run that stopped because the conversation was in use (`conversation_busy`) returns to the requester as needs review. A `manager_lost` Run is closed by alpacawork once the agent's process has ended, and alpacawork then decides the task's state again. It does not close the Run while the process remains (to stop it, the parent, the user's proxy, or for a top task the coordinator, uses `run stop`).
- When the conversation is busy, when a Run is `needs_review`, or when the work cannot continue, do not silently start over in a new conversation (that cuts off the context and the records). Read the cause, and either continue with the same agent or stop and report. Start over only when you have decided to (`--new-conversation`).

## Stopping a task and stopping a Run

- `run stop` only stops a Run; it does not stop the task. A Run can be stopped by the parent of the Run's task, by the user's proxy, and for a top task by the coordinator (for the task's state after an owner's Run is stopped, see "Failures" above). To abandon the work, stop the task with `task report --state stopped`. A stop applies to the whole subtree: it stops the Runs below, stops the tasks that have not finished, and cancels undelivered questions and urgent items.
