# Owner

## Start or resume

1. Read the latest task, request and project policy as described in [the main skill](../SKILL.md#when-you-start-or-resume).
2. Before writing your first progress report or planning the work, use [Open the skills for your next action](../SKILL.md#open-the-skills-for-your-next-action) for those purposes. Open the matching skills now and apply them to the report and plan.
3. Give the estimate for the end report as described below.

## Responsibilities

- At each breakpoint, check that the task's title still matches the work and results as currently approved. If it is out of date, fix it with `task update --task <your ID> --title "<new title>" --expected-task-hash <hash>`, using the latest hash. This does not widen the scope of the request, and it does not answer a question or approve a result on anyone's behalf. The `--title` of a report is the report's title; it does not change the task's title.

- Updating the task's values and reporting its state are the owner's job. Before you end a turn, leave one of these: an end report (`task report --state done`), a question to a recipient you chose (`--state waiting --ask-to <ancestor Task ID>|user`), or an open request (a `task request` to a member or a child). If you end the turn with none of them, the task fails (no report). Neither a `doing` report nor a record counts as one of these.
- Record the work you did in History as described in ["Recording work" in the main skill](../SKILL.md#recording-work).
- For progress along the way, record only the milestones, with `task comment` (it wakes no one; for what counts as a milestone, see ["Recording work" in the main skill](../SKILL.md#recording-work)). Only the last thing you write in the conversation appears on the screen, so put any milestone you want kept into a record.
- When you start, and whenever you receive an instruction or a send-back (including one that joins a conversation already running), give an estimate of the time until your end report before starting the work. An instruction that arrives voids the estimate so far, and the screen shows no expected report time until you give a new one.
  - Estimate the minutes until you report the end (`done`), including round trips with members and reviewers, rebasing onto main, and tests. If you cannot estimate, leave the reason in the report's title.
  - Look at the estimate examples in the launch prompt (estimates and actuals for the same agent and the same launch selections) and base your estimate on the actuals. Do not copy an earlier estimate. `estimateMinutes` is the minutes last declared; `actualMinutes` is the minutes the task was `doing` until the report that made it done or awaiting review.
  - When a continuation was woken only by a return from a member or a child, report `doing` with a new estimate if the time your last estimate named has passed or the return moves it; otherwise do not report `doing` (the continuation already counts as In progress without it). The row of a task with children shows the latest estimate among it and the tasks under it, so a passed estimate of yours reads as overdue once the children are done.
  - Use the latest hash and run, for example, `alpacawork task report --task T42 --state doing --estimate-minutes 20 --title "Work up to the end report" --description-file <file> --expected-task-hash <latest hash>`.
- Assign members, request work from them and release them yourself (`agent assign`, `task request --agent`, `agent release`). As the owner of the child's parent task, you are the one who assigns, hands over and releases the owner of a direct child (`agent assign`, `agent handover`, `agent release`) and who stops a child's Run (`run stop`). If an agent does not fit, stop it and replace it. In a request or a send-back you can choose the model and so on with `--selected` (the values you can choose are the `params` of agents in `alpacawork config get`; for how to write them and which value is used, see `task request -h`). The request is refused if the previous value, or the value set at assignment, has gone from the configuration; choose again or start a new conversation. Also start a new conversation after changing the kind of adapter an agent uses. You can move a direct child within the subtree under your own task (`task move`).
- The user can put your task on hold from any state; its state then becomes `held`. You cannot take your own task off hold. You can decide to take a direct child off hold, following ["Hold" in "Delivery and completion"](lifecycle.md#hold), but if your own task is on hold, first have your parent, the coordinator or a person take it off hold. While your task is on hold, all you can do is report `doing`, ask a question, withdraw a question, and add records. You cannot create children, update values, request work from members, assign or release them, or report an end (`done` or `stopped`).
- When you need to be replaced, or your task needs to be moved, archived or deleted, ask whoever fits the nature of the matter ("Limits of your responsibility and whom to ask").
- If you own a top task and receive an answer from the user that changes direction, check that it is reflected in "User instructions"; if it is not, fix it as `field get` says to write that field. For requests to children and members, follow [Tasks and requests: the common procedure](request.md): hand each its share of the work without copying the user's original words.

## Handover

- When the owner changes on a task that is in progress, awaiting review or failed (except one awaiting review without a Run), the new owner receives a "handover" notice (the current state, the open requests, and the returns and notices not yet handled). Read the notice and `task get --task <your ID> --include closedQuestions` (the values, the `questions` your task asked, the `incomingQuestions` addressed to it, and the related `relevantAnswers`), and also fetch the fixed full text of each original question (the question an answer is for) that your task asked and that was withdrawn on resume, before you continue. A question addressed to you that was received but not answered stays on the task it is addressed to, and the new owner handles it. The records of the questions, requests and answers the previous owner made also stay on the same task, and their returns reach you; but the old waits your task had open close when the handover's continuation is accepted.

## Choosing who does the work

Keep the making and the judgment about the next step with the same agent. Whoever makes a result is the one who can settle what to do when it goes wrong, so make that agent the result's owner. Separate the two only when the judgment does not stay inside the result. Size alone does not decide it.

- First settle who makes each result: the agent the project policy names for that work; where it names none, you. A separate result that can proceed in parallel with your own making, sharing no decisions with it, goes to another agent.
- Do it yourself: the judgments about your task as a whole (what the request asks for, how to split the work, which option to take, whether the result is good enough to report), and the results that you make. The judgments of the whole stay with you whatever you hand over.
- Ask a member: help with your own judging and making. You read the reply and settle what comes next.
- Make a child: a result that another agent makes, when the judgments about its next steps stay inside it. Assign that agent as the child's owner, even when this result is all that remains of your task. The child's owner settles what to fix, how to check, what to ask and whom, and when it is done. You check its result against the done conditions, as "Receiving a child's result" below says.
- The judgments stay inside a result when no way of settling them changes what the request asks for, another part of your task, or the done conditions and the scope of approval you were given. Look at parts whose decisions change together as one result. If the judgments do not stay inside, ask a member instead and settle them yourself. Do not make a child for small work.
- The reason: a member cannot ask questions or place agents, so it cannot carry judgments that need a question or another agent; a child's owner can do both.

## Creating children and requesting work

- A child that has only been created is a plan (not started, with no owner). Before you request work from it, assign it an owner with `agent assign`. A task with no owner cannot be put to work, and no children can be created under it.
- When the user asks this task for an additional result, it arrives as an ordinary instruction to you. Decide whether children are needed as "Choosing who does the work" above says. Only you (this task's owner) can create children.

## Waking and waiting

- Whenever you are woken, including when you start, resume or take over, and whatever woke you (a child's question, a message from the user or the parent, an answer, a member's return, and so on), re-read with `task get --task <your ID> --include closedQuestions` the latest values, the `questions` you asked (including withdrawn questions), the `incomingQuestions` addressed to you, and the `relevantAnswers` you need (for what closes an old wait, see ["Questions" in "Delivery and completion"](lifecycle.md#questions)). Read the withdrawn waits listed in the launch prompt and the original questions in `questions` with `task get --task <your ID> --question <question ID>`, and check them against this input, the answers and the children's latest status. For a question that the launch prompt carries only as a summary or a read command, also fetch the fixed full text with `task get --task <asking task> --question <question ID>`. Judge for yourself whether the words that arrived settle the unresolved points.
  - A decision is still needed: leave out the points already resolved, gather the points still needed into the "Questions" (`decide`) value, and ask anew with `alpacawork task report --state waiting --ask-to <ancestor Task ID|user> --title "<title>" --description-file - --values-file <values JSON> --expected-task-hash <latest hash>`. Only one option can read `-`; the other needs a regular file (a pipe such as `<(…)` is refused). Do not revive the old question even if the content is the same. While on hold, ask only if you can do so with the values as they stand, without `--values-file`.
  - The decision is settled: remove the old question from `decide`, carry on with the work, and leave an end report, a new question or an open request. A withdrawal in itself is not evidence that a point was resolved.
- If another point comes up while you work in the same Run, regroup the unresolved points into one question. Do not combine points that go to different recipients: ask the one whose answer is needed first, and leave the other in the "Remaining work" field. When a late answer arrives, likewise merge the reply to the original question into the latest points before you ask again; do not repeat the same question mechanically.
- To save values only, use `task update --values-file`. After resuming you need a new question, an open request or an end report; do not end the turn leaving only a withdrawal. When an open question of yours is no longer needed, you can withdraw it with `task report --withdraw <question ID> --expected-task-hash <latest hash>`.
- Read the details of "Open work" in the launch prompt with `task get --task <ID> --include openObligations`, returns and notices with `task returns`, and a member's result with the `run get` command you were given. Keep receiving a notice distinct from answering and from accepting a result.
- The per-child changes in the launch prompt tell you which children changed since you last reported together with values (children that are done, moved or deleted included). When the section is too large, it is replaced by a read command; in that case read the list with `task list` and fetch the children you need with a `task get` for each.
- On the first turn of a task that has dependencies, read with `task get` how each dependency ended before you start.

- After you request work from a member or a child, end the turn without changing the state. The continuation starts automatically with all the results that have arrived. While open requests or unfinished children remain, do not report your own task (their parent) done, even after you have processed results (for how waking works, see ["Delivery and completion"](lifecycle.md)).
- Do not wait for a member's or a child's Run inside your own Run. While you wait, your own Run keeps going and occupies a parallel slot, and in a workspace that limits run time, your Run is stopped when it reaches that limit. alpacawork wakes you to tell you that the Run has ended.

## Receiving a child's result

- You receive a child's result after its request closes, together with everything else that has arrived by then. Receipt does not wait for other requests to close. For acceptance, verify before you report the end whether the results of your children and members meet your done conditions (for how to verify, see ["Checking a result against the request" in the main skill](../SKILL.md#checking-a-result-against-the-request)). If something is missing, have the same agent fix it with `task request`.
- A request to a child also stays open while that child has a question open ([Waking](lifecycle.md#waking)).
- For a failed child, you decide first: have the same owner retry with `task request`, or stop the child with `task report --task <child> --state stopped`. Two cases appear in the user's turn ([Waking](lifecycle.md#waking)) and are decided by the user: a child that stopped for one of these reasons (a limit, a delivery whose receipt is unknown, a failure to launch, a missing configuration), and a failed request that the user made directly to that child. If retrying does not fix it, ask the user.
- If a child is put on hold or taken off hold while your request to it is open, a notice wakes you. A hold means the user has set the task aside. Decide whether to wait or to go on with other work.

## Limits of your responsibility and whom to ask

- First read the request's inputs, its expected results, and the limits of your responsibility and of what you may decide. Within the read access you already have, use `task list` / `task get` / `run get` to fetch for yourself the results of sibling and neighbouring tasks that you need. Any way of building that leaves those limits and the shared contracts unchanged is yours to decide; go ahead with it. Do not stretch permission to read into permission to instruct changes in other branches or to change definitions outside your responsibility.
- When a change is needed to a definition outside your responsibility, to a shared contract or in another branch, find out from the results, the requests and the current tree who holds the definition to be changed, and put the question directly to the owner of the nearest valid ancestor task that can handle that change. Do not relay everything through your direct parent as a matter of course. A change to a person's purpose, values or conditions, and an approval that remains with a person, go to `user`. Do not give a project's ID in place of a person.
- Before deciding what to ask the user and drafting the question, follow [Open the skills for your next action](../SKILL.md#open-the-skills-for-your-next-action). Ask with `task report --state waiting --ask-to <ancestor Task ID>|user`, and write the questions in the "Questions" value (`decide`; for how to write it, see `field get`). Give each question its kind in `decide_kind`: `accept` when it asks whether a result you made can be taken (merged, adopted, released), `choose` when it asks the reader to pick among options; a question without it is refused, since how often a result is taken as first made is counted from it. The reader sees the report's description and, right under it, each question with its choices and note, as one page. Show each picture and link once on that page, and do not explain the same thing twice: in the description, briefly, what holds whichever choice is taken (the result, its evidence, what is unchecked); under each choice, what that choice changes; in a note, only what that question needs and the page does not say yet. Include the change needed, the facts you read yourself, and the limit of responsibility you want decided. State the recipient explicitly according to the nature of the question; name even your direct parent by ID. The recipient is explicit and separate from the requester that returns go to, and you can ask while children or members are running. For the specifics of saving, answering and withdrawing, follow ["Questions" in "Delivery and completion"](lifecycle.md#questions).
- If you receive a question that was addressed to the wrong recipient, do not decide it yourself: return the appropriate Task ID, or `user`, with the reason, as an ordinary answer to the original question. The asking task re-reads the current definitions and asks anew. Do not re-address the original question, and do not forward another question on its behalf. If a condition that only a person can decide arises while you are deciding, ask the user that one point yourself and leave its relation to the original question in your values. Once you have the person's answer, see it through to answering the original question.

## Passing decisions down and answering the original question

- If the decision is yours to make, read the original question and the related results, and send an ordinary `task request --task <direct child> --instruction-file ...` to each branch directly below you that needs a change. Each owner passes it down in turn, parent to child, until it reaches the agent that holds the definition. Do not wake unrelated branches, and do not stretch an ancestor's right to answer into a right to instruct grandchildren or other branches. In the request, state in plain sentences the original question ID, the asking task, what was decided, and where it needs to be applied.
- Confirm that the server accepted the requests to the branches that need them, and in the same turn answer the original question with `task request --task <asking task> --answers <question ID> --instruction-file ...`. Before you answer, check with `task get --task <asking task> --question <question ID>` whether it is open. If its full text ends with `Stop:` and stopping is your decision, stop the asking task with `task report --task <asking task> --state stopped` instead of answering. Even if it has been withdrawn or answered, send your reply under the original question ID (it then arrives as an ordinary instruction, and the asking task judges its meaning and starts moving); do not re-attach it to the current question. Write the decision, where you passed it down, the work that can be done now, and the acceptance conditions for the results that work depends on. The asking task receives the answer to the original question, so do not send an ordinary instruction with the same content on top of it. The asking task reads the answer and the latest requests and results, and judges whether the point is settled in substance and whether to continue the work.
- If only some of the requests were accepted and the rest were refused or their save is uncertain, do not treat the decision as fully passed down. Leave the original question open, and leave in your values what was accepted, what is not done, and the condition for resuming. After resuming, check the existing requests against the results and carry out what is not done. Neither the saving of an answer nor the server's acceptance of a request proves that the result has been applied.
- Coordinate the release and the ordering of needed definitions and partial results through the existing questions, ordinary instructions and answers. If you are the one who applied the change, report the result and its fixed version, and ask the valid ancestor that decides on resuming, "May work resume on this version?", giving the original question ID and the conditions. The decider reads the version and returns the answers needed to the releasing side and to the original question that is waiting to resume. There is no need to wait for the whole branch to be done. Do not create a dedicated ledger or mechanism for this coordination, and do not use an urgent record in its place.
- Continue the work that the question does not affect. If there is no work to go on with, end the turn leaving a question you asked or an open request, and a note of what must arrive, and from whom, before you can resume. Having only a question addressed to you is not a valid condition for waiting. If, after the decision, you are still waiting for a result you depend on, ask the appropriate ancestor a coordinating question, attaching the version you read yourself and the conditions still missing. Do not create a question that only waits for an acknowledgement or only asks how things are going.
- In a question you ask after being stopped at the limit on automatic launches, write that an answer to the open question alone does not reset the count, and that whoever answers has to send the continuation to you as an ordinary `task request` (without `--answers`) that quotes the user's words. When the server accepts the continuation, the old question is withdrawn, so re-read the unresolved conditions and include them in the latest question if needed. A hold has to be taken off explicitly, as in ["Hold" in "Delivery and completion"](lifecycle.md#hold); a failure or an unknown receipt goes through whoever already has the authority to resume it and the existing procedure. Do not treat a question or an answer as having lifted any of these.
- When something has had an effect outside your scope, tell the requester, even after you have dealt with it. For a record that the requesting parent must read at once, use `task comment --urgent "<reason>"`; for an end that the parent must act on at once, use `task report --state done --urgent "<reason>"`. These are refused when the requester is the user, so if a decision is needed, ask the user.

## Reporting the end

- When the user is your requester, `done` asks them only to accept the result (awaiting review); it does not ask them to decide. If they asked for something to adopt or choose from (a proposal, for example), their choice is part of the task: ask it as a question to `user`, and do not report `done` with the choice left in the report text or in "Remaining work". Do not make a question of a decision that is yours to make, or of a follow-up the user did not ask you to propose.
- Reporting `done` withdraws any open question you asked. If you need to wait for the answer, do not report `done`. An answer that arrives after the withdrawal becomes an ordinary instruction. You cannot finish while a question addressed to you remains.

- Before judging the result ready, follow [Open the skills for your next action](../SKILL.md#open-the-skills-for-your-next-action) for reviewing it. When you have finished, report with `task report --state done --title "<result>" --description-file <file or ->`. Always write a nonblank description: what changed, how it was verified, and what remains. Task values such as `conclusion` and attachments do not replace the report description. The server decides where the report goes (["Done and awaiting review" in "Delivery and completion"](lifecycle.md#done-and-awaiting-review)).
- Do not write an addressee or the names of screen buttons in a report. The screen changes, and pointing the user to a button that is not there confuses them.
- When awaiting review is lifted (for the rules on lifting it, see ["Done and awaiting review" in "Delivery and completion"](lifecycle.md#done-and-awaiting-review)), read the new words and the timeline, the original result report and the children's latest status, and decide what to do next. After you fix things, update the values and report `done` again. Do not treat the fact that a task is no longer awaiting review as the user's acceptance.

## Reports

- Ask yourself the question below at the breakpoint where you move on to the next substantial result; after you take in an instruction or an answer that changes direction; when fixes for the same shortfall keep going without progress or new evidence; and before you ask for a decision or return a result. If you suspect a detour, check without waiting for a breakpoint.

  > How does the work I am doing now lead to achieving the current goal? If I thought it through without carrying over the approaches so far, would I still choose this work next?

  Establish the current goal from the original request and the changes the requester approved; do not compare against your own summary alone. "Without carrying over" means letting go of attachment to an approach; keep the verified facts, results, decisions, approvals and safety boundaries. Do not settle for "it is for quality": check, against the actual thing or counter-evidence, what the work lets you verify, complete or decide. Necessary investigation, and rework in response to new evidence, count as contributing.
- For rework on the same result, normally continue the conversation. If the contribution is unclear, tie the next piece of work back to the goal; if it is a small course correction, carry on as you are. If the direction or the chosen approach has changed greatly, if you keep going back to old assumptions, or if unneeded re-reading is large, choose whether to update the snapshot and rebuild in a new conversation. If the goal is already achieved, report the end; if the goal or the scope needs to change, ask whoever holds that decision. Do not switch on counts or elapsed time alone, and do not make this a ritual for every tool call or every notice.
- Scale signals (the numbers are guides, not conditions for stopping): when the values exceed their guide sizes or the task folder exceeds about 1 GB, do the tidying described in [Tidying accumulated information](upkeep.md#tidying-accumulated-information) at the next safe breakpoint. When you have extended the estimate for the same scope twice in a row (or it has passed twice the first estimate, or you remain unable to estimate), when you were stopped at the limit on automatic launches, or when returns keep waking you but the remaining work does not shrink, go back to the done conditions in your request text (see [Tasks and requests: the common procedure](request.md)). From the must-fix problems that remain and the results that can be reused, choose again which supporting work to drop, a simpler way of doing the work, how to split it, and where to break for reviews and tests. Do not settle for an extension alone; leave one milestone record of the decision and the reason.
- Keep the values at a length where the current situation and what remains can be seen at a glance. The guide is about 2,000 characters in total; for each field, it is the character and item guide at the head of that field's writing instructions in `field get` (the maximum length is about 1.3 times that). Write the decisions now in effect and their reasons, the old assumptions they replaced, the unverified points that could change a decision, and the next step and where, in the fields that fit (if none fits, at the top of the "Notes" field). Write the values too as a report the user reads: do not string together abbreviations, SHAs or Run numbers (write a version or a location once only, on its deliverable's line). When you are about to exceed the guide, cut from the history and from what is already done, and keep "User instructions", the done conditions, reservations and unverified points (exceed the guide rather than drop those).
- At the start, put the purpose, the boundaries, the locations and the next step into the values. Save the values at the milestones of a change of direction, an adopt-or-reject decision, an important failure or a result, and before you wait or return. Also at a safe breakpoint where an interruption is in sight, record side effects, unverified points and resources first. Record in the existing fields, too, what you are waiting for and from whom, the approval conditions, and the number of reviews used.
- When you add, rewrite. Delete finished items from the remaining work, values that are out of date, and the history of matters that are closed, and fold what is still needed into one line of the "Conclusion" field. Values are overwritten, and no old version is kept. Maintain "User instructions" as `field get` says to write it. For other decisions and grounds that will be needed later, confirm where they can be retrieved from, such as a question or a Run, and leave one line on how to get them; if they exist only in the values, keep them. Do not make a file that copies the old values wholesale. For attempts and rejected options, write one line with the reason only for those likely to be repeated. Do not make a retrospective section or a list of every attempt.
- To report a snapshot, save it together with the state report by adding `--values-file <absolute path of the values JSON>` to `task report --state doing|waiting|done`, and add `--next-conversation new` as well if the next conversation is to be a new one, or `--next-conversation compact` (with `--compact-focus` for what the summary must keep) if it is to continue compacted first. A doing report alone does not let you end the turn, so the rule in "Responsibilities" to leave an end report, a question or an open request applies all the same. Reporting `doing` in the same Run after you asked a question withdraws that question, so attach the values to the question's report itself. For the choice of conversation, including an explicit new one chosen on the requesting side, follow [Tasks and requests: the common procedure](request.md).
- A report's `--values-file` also declares that you have reflected in the values the child versions that arrived in full in the launch prompt. Check the conclusions of cancelled, moved and finished children as well, and do not mark a result you have not read as accepted. To edit values only you can use `task update --values-file`, but it declares neither child versions nor an intent to make the next conversation a new one, and it voids an earlier intent. Read the source of truth for states, questions and requests from the server's records.
- If an instruction arrives after you saved, the old intent for the next conversation (new or compacted) is void. An ordinary state report without values that you send afterwards also cancels the intent, so attach the values and the intent to your last report. Handle the instruction in the current conversation, then report once more: the values, updated with your new judgment, together with the intent. If the next conversation's receipt is unknown or the conversation is in use, do not escape into a new conversation; check the records and report. An unknown receipt is resolved by an ordinary new request from the user, after which you continue. Do not specify `--new-conversation` while the receipt is still unknown.
- Even when you change conversations, carry over the unverified points, the pending approvals, the review count and the open work. Do not stop the children running in parallel across the board; record which version you are waiting for and from whom, what you will decide, and the stage the side effects have reached. Switching is no substitute for approval or acceptance; an action that depends on approval waits until the actual answer.
- Before you report, read the latest `task get` and `field get`, rewrite the fields that are out of date with their latest values, and send them. Do not send fields that have not changed. A list field is replaced whole, so send the whole list as it should now read; do not just append new items while keeping stale ones.
- Check how to write `--title` and `--description-file`, and their lengths, in `alpacawork task report -h`. Put images in the task folder and reference them as `![purpose](relative path)`. Before drafting the report, follow [Open the skills for your next action](../SKILL.md#open-the-skills-for-your-next-action).
- Where a description, a choice's description or a note first names something the reader can open (a PR, an issue, a commit, a web page, a file in the task folder), make the name a link: `[PR #100](https://github.com/<owner>/<repo>/pull/100)`.
- An example of writing the description without creating a temporary file (attach the latest hash):

  ```sh
  alpacawork task comment --task T42 --title "Checked the investigation results" --description-file - --expected-task-hash <hash> <<'EOF'
  Write what you looked into and what you will do next.
  ![comparison image](compare.png)
  EOF
  ```
- Decide where evidence and working files go by what they are for. Put deliverables, and whatever is needed for the user's acceptance, for review, for finding a cause or for resuming (comparison images, a document stating the conclusion, a record of a problem not yet solved, and so on), in the task folder (`$ALPACAWORK_WORKSPACE/tasks/<ID>/`; `task file put` can also put files there; it is the "Files" tab on the screen), and only the minimum needed, so that they can be read across a change of agent or a restart. Do not put copies of working trees or caches, or backup tars, there. As the owner, delete things in the task folder as ordinary files at the breakpoint where their purpose has ended (the decision is made and the requester has accepted, or the problem is fixed); for things a member put there, go by the locations written in its reply. Do not delete deliverables, things the user has not yet seen, evidence the requester still needs in order to finish checking a result for acceptance, or records another skill has decided to keep (such as a plan). A temporary location can be wiped by a restart, so do not keep evidence you still need only there. List in the Deliverables field every file the user should open: the Files tab shows those first, then other documents and media outside `work/`. Keep what only agents use (logs, scripts, raw output) in `work/`.
- Before you report the end, fill in the "Running processes" field: "none" if there are none; otherwise whether each is temporary or permanent, where it is, how to stop it, and why (["Guardrails" in the main skill](../SKILL.md#guardrails)). If that field does not exist, write this in the "Notes" field.
